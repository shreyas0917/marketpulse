# MarketPulse SLOs

These are **project targets** for a synthetic market-data service, not claims of achieved
reliability. The SLO window is a rolling **30 days**. Local demos run for minutes or hours, so any
number measured locally says so and gives its window.

## What users of market data care about

A quote consumer needs a price that is **there** (availability), **fast** (latency) and **current**
(freshness). Freshness depends on the ingestion path, so ingestion lag is an SLO in its own right:
it catches a slowing pipeline before quotes visibly go stale.

## SLIs and targets

`Q` = `route="/v1/quotes/{symbol}"` (route template, never the raw path).

| SLI | Good event | Valid event | Target | Error budget |
|---|---|---|---|---|
| Availability | quote response that is not `5xx` | every quote response | 99.9 % | 0.1 % |
| Latency | quote request answered in < 250 ms | every quote request (any status) | 99 % | 1 % |
| Freshness | returned quote with `age_seconds` < 2 | every returned (`200`) quote | 99 % | 1 % |
| Ingestion lag | event written within 1 s of its event timestamp | every written event + every dead-lettered event | 99 % | 1 % |

```promql
# Availability: 4xx (unknown symbol, no quote yet) are client errors and count as good
good:  sum(rate(http_requests_total{Q, status!~"5.."}[w]))
total: sum(rate(http_requests_total{Q}[w]))

# Latency: a fast 503 is "fast" here but bad for availability
good:  sum(rate(http_request_duration_seconds_bucket{Q, le="0.25"}[w]))
total: sum(rate(http_request_duration_seconds_count{Q}[w]))

# Freshness: stale degraded-mode quotes (age > 2 s) are bad; 503s record no age
good:  sum(rate(quote_age_seconds_bucket{le="2.0"}[w]))
total: sum(rate(quote_age_seconds_count[w]))

# Ingestion lag: dead-lettered events never get a lag observation, so they are added as bad
good:  sum(rate(ingestion_lag_seconds_bucket{le="1.0"}[w]))
total: sum(rate(ingestion_lag_seconds_count[w])) + sum(rate(events_processed_total{result="dead_lettered"}[w]))
```

### Exclusions

- `/health/*` and `/metrics` have their own route labels and never match `Q`.
- Requests with `X-Traffic-Class: warmup` (the first 10 s of every k6 run) are recorded under
  `route="warmup"` and record no quote age.
- Duplicate and out-of-order events are processed correctly but are not "written", so they record
  no ingestion lag ([DECISIONS D8](DECISIONS.md)).

### Measurement points

| Metric | Observed | Value |
|---|---|---|
| `http_request_duration_seconds` | API middleware, every request, any status | receipt → response sent |
| `quote_age_seconds` | every `200` quote, from Redis or local cache | response time − event timestamp |
| `ingestion_lag_seconds` | worker, every successfully written event | write time − event timestamp |

Ingestion lag compares clocks on two hosts (producer and worker). They are assumed NTP-synced;
skew shows up directly as lag. On a single Docker host or kind cluster they share a clock.

### Histogram buckets

An SLO threshold can only be measured exactly when it is a bucket boundary, so each threshold is an
explicit `le`. **Changing a target means changing the bucket list in the same commit.**

Prometheus 3 normalises classic-histogram `le` labels to their float form on ingestion, so the
selectors are `le="2.0"` and `le="1.0"` (not `le="2"` / `le="1"`, which match nothing).
`tests/unit/test_slo_buckets.py` fails if any rule, dashboard or canary query uses an `le` value
that is not a bucket boundary in exactly that form ([DECISIONS D17](DECISIONS.md)).

| Metric | Buckets (s) | SLO boundary |
|---|---|---|
| `http_request_duration_seconds` | 0.005, 0.01, 0.025, 0.05, 0.1, **0.25**, 0.5, 1, 2.5, 5 | `le="0.25"` |
| `quote_age_seconds` | 0.1, 0.25, 0.5, 1, **2**, 5, 10, 30, 60 | `le="2.0"` |
| `ingestion_lag_seconds` | 0.05, 0.1, 0.25, 0.5, **1**, 2, 5, 10, 30 | `le="1.0"` |

## Alerting

Recording rules `sli:<sli>:error_ratio_rate<w>` for `w ∈ {5m, 30m, 1h, 6h, 3d}`
([slo-recording.yml](../observability/prometheus/rules/slo-recording.yml), generated by
[gen-slo-rules.py](../scripts/gen-slo-rules.py)). Burn rate = error ratio ÷ budget.
Multi-window, multi-burn-rate alerts (Google SRE Workbook):

| Alert | Severity | Long / short window | Burn rate | Budget used when it fires |
|---|---|---|---|---|
| `<Sli>FastBurn` | page | 1 h / 5 m | 14.4× | 2 % |
| `<Sli>FastBurn` | page | 6 h / 30 m | 6× | 5 % |
| `<Sli>SlowBurn` | ticket | 3 d / 6 h | 1× | 10 % |

The long window gives significance; the short window makes the alert resolve soon after the cause is
fixed. Every alert has a runbook in [runbooks/](runbooks/). Rules are unit-tested with
`promtool test rules` (`make rules-test`), with must-fire and must-not-fire cases for each SLI.

### Gaps a ratio cannot see

| Gap | Alert |
|---|---|
| Worker stopped or stalled: nothing processed, ratio empty | `IngestionStalled`: `max(queue_oldest_event_age_seconds) > 10` for 2 m |
| No quote traffic at all: ratio empty | `QuoteTrafficAbsent`: quote request rate is 0 (or absent) for 5 m |
| Redis down while the cache still serves: availability looks fine for up to 30 s | `QuoteStoreDown`: `min(quote_store_up) == 0` for 1 m |
| Events stuck in the DLQ (incl. SQS redrive-policy messages the worker never counted) | `DeadLetterQueueNotEmpty`: `max(dlq_depth) > 0` for 1 m |
| A service cannot be scraped | `TargetDown`: `up == 0` for 2 m |

## Error-budget policy

| Budget remaining (30 d) | Policy |
|---|---|
| > 50 % | Normal. Feature releases continue through the canary pipeline. |
| 25–50 % | Releases continue; every release needs a rollback plan; review recent burns weekly. |
| < 25 % | Feature releases are frozen except reliability fixes. The top error source gets a named owner. |
| Exhausted (≤ 0 %) | Full freeze until the budget recovers above 25 %. A postmortem is required for each incident that used > 10 % of budget. |

Any single incident that consumes more than 2 % of a budget (that is, anything that pages) gets a
blameless postmortem using [the template](incidents/TEMPLATE.md).

## Degraded mode and its limitations

Redis is the source of truth for latest quotes. Each API pod keeps a bounded in-process LRU cache,
one entry per configured symbol, refreshed on every successful Redis read. When a Redis call fails
or exceeds 50 ms:

1. a cached quote no older than `STALE_QUOTE_MAX_AGE_SECONDS` (30 s, by event timestamp) is served
   with `stale: true`, `source: local_cache`;
2. otherwise the API returns `503 {"error": "QUOTE_UNAVAILABLE"}` with `Retry-After`.

The API never serves an arbitrarily old price. **Limitations:**

- The cache is **per pod**, not shared. Two pods may return different stale values, or one may
  return 200 while another returns 503.
- It is **lost on restart**. A pod started during a Redis outage has an empty cache and returns 503
  for every quote.
- It only holds symbols that pod has served recently. Rarely requested symbols will likely 503.
- After 30 s of outage, every pod returns 503. Degraded mode buys time; it is not a replacement
  for Redis.

**Readiness ignores Redis on purpose.** If `/health/ready` failed whenever Redis was down, every pod
would leave the load balancer at once, degraded mode would never be reached, and users would get
load-balancer errors instead of controlled responses. Redis health is tracked by `quote_store_up`
and the `QuoteStoreDown` alert instead.
